# Getting started with `pell` v0.1

This is the **v0.1 MVP compiler** for the language designed in
[`design.md`](./design.md). It is a Python-based transpiler that takes
`.pell` source and emits Oracle PL/SQL 23. A future Rust implementation
is the long-term plan; this exists so you can write code and see what
comes out *today*.

> Status: hand-written subset compiler. 75 tests pass. 7 example
> programs compile end-to-end. Around a dozen known limitations (see
> "What doesn't work yet" below).

## Quickstart

```sh
# from /Users/shaun.batterton/code/plsql

# compile a single file to stdout
./pell build compiler/examples/01_hello.pell

# compile a single file to disk
./pell build compiler/examples/02_employees.pell -o /tmp/employees.sql

# compile every .pell in a directory
./pell build compiler/examples -d compiler/expected

# generate a merged pell_runtime.sql with EXCEPTION decls for every error variant
./pell runtime compiler/examples -o compiler/runtime/pell_runtime.sql

# print the AST or token stream (debugging)
./pell parse  compiler/examples/02_employees.pell
./pell tokens compiler/examples/02_employees.pell

# run the test suite
cd compiler && PYTHONPATH=. .venv/bin/python -m pytest tests/ -v
```

The `pell` wrapper at the repo root finds the project's venv and runs
`python -m pell` for you. No global install needed.

## Example: hello

```pell
// hello.pell
module hello;

import std::log;

pub fn greet(name: text) {
  log::info(name);
}
```

```sh
$ ./pell build compiler/examples/01_hello.pell
-- Generated by pell v0 from module hello
-- DO NOT EDIT — regenerate with `pell build`

CREATE OR REPLACE PACKAGE hello AS
  PROCEDURE greet(p_name IN VARCHAR2);
END hello;
/

CREATE OR REPLACE PACKAGE BODY hello AS

  PROCEDURE greet(p_name IN VARCHAR2) IS
  BEGIN
    log.info(p_name);
  END greet;
END hello;
/
```

## What works

| Feature | Example | Notes |
|---|---|---|
| `module foo.bar;` | `compiler/examples/01_hello.pell` | lowers to `foo_bar` package |
| `import std::log;` | `02_employees.pell` | parsed; uses `log.info(...)` in lowered code |
| `pub` modifier on items | everywhere | controls spec visibility |
| `record` decl | `02_employees.pell` §4.2 | emits `TYPE … IS RECORD` |
| `error` decl with payload | `02_employees.pell` | emits `EXCEPTION` + `PRAGMA EXCEPTION_INIT` in `pell_runtime` comment block |
| `fn` (procedure + function) | all | Unit return → PROCEDURE; T → FUNCTION |
| `Result<T, E>` / `?` | `02_employees.pell` | errors via `RAISE`; `?` is a no-op at runtime (raise propagates) |
| `Option<T>` / `T?` | partial | nullable via NULL; no two-tag lowering yet |
| `sql! { SELECT ... }.one()?` | `02_employees.pell` | SELECT INTO with `NO_DATA_FOUND`/`TOO_MANY_ROWS` re-raised |
| `sql! { SELECT ... }.first()` | (not in examples) | cursor FOR loop with `FETCH FIRST 1` |
| `sql! { INSERT ... RETURNING id }.returning::<number>().one()` | `04_inventory.pell` | DML with `RETURNING INTO` |
| `sql! { UPDATE ... }.rowcount()` | `04_inventory.pell` | DML + `SQL%ROWCOUNT` assignment |
| `for x in sql! { ... } { ... }` | `05_iter.pell` | cursor FOR loop |
| `transaction { ... }` | `03_transfer.pell` | SAVEPOINT + COMMIT + ROLLBACK on error |
| `if/else` | `02_employees.pell`, `03_transfer.pell` | IF/THEN/ELSE/END IF |
| `match` with `Some`/`None`/`Ok`/`Err` | (parsed) | partially lowered — see "doesn't work" |
| `return Err(Foo { ... })` | `02_employees.pell` | calls `pell_runtime.set_err` then `RAISE` |
| `return Ok(x)` | `02_employees.pell` | RETURN x; (or just RETURN; for procedures) |
| `record.field` access | `03_transfer.pell` | direct PL/SQL field access |
| Binary operators | `02_employees.pell` | `==` → `=`, `!=` → `<>`, `&&` → `AND`, `||` → `OR`, etc. |
| Annotations: `@deterministic`, `@result_cache`, `@udf`, `@autonomous` | `06_annotated.pell` | render onto signature / as `PRAGMA`; conflict detection enforced (`@udf` + `@autonomous` errors at compile time) |
| String interpolation: `"hello {name}"` | `07_full.pell` | lowered to `'hello ' || p_name`; supports field paths `{p.id}` |
| `.for_update()` / `.nowait()` / `.skip_locked()` / `.wait(N)` / `.for_update_of(cols)` | `07_full.pell` | locking modifiers on read iterators |
| `pell runtime` CLI subcommand | — | aggregates all error decls from a project into a merged `pell_runtime.sql` |
| `fn name() { ... } finally { ... }` | `08_finally.pell` | nested `pell_finally_body` procedure called on both success and error paths; RAISE on error path |
| `let xs: list<T> = [v1, v2, ...]` | `09_bulk.pell` | declares `TYPE t_T_list IS TABLE OF T INDEX BY PLS_INTEGER` at the package body, emits per-index assignments |
| `for x in xs { ... }` over a list | `09_bulk.pell` | `FOR i_x IN l_xs.FIRST .. l_xs.LAST LOOP` with a shadow local for the loop variable |
| `forall x in xs { sql! { ... :x ... } }` | `09_bulk.pell` | emits PL/SQL `FORALL` over the list; body must be a single DML sql!{}; `:x` substitutes directly to `l_xs(i_x)` |
| `let rows: list<T> = sql! { select … }.collect();` | `09_bulk.pell` | emits `SELECT … BULK COLLECT INTO l_rows FROM …` and declares the assoc-array list type |

## What doesn't work yet

Roughly ordered by how much pain they'll cause if you hit them:

1. **`match` arms are limited.** Variant patterns (`Some(x)`, `Err(NotFound { id, .. })`) are recognized but the lowering is a coarse `BEGIN ... EXCEPTION ... END` wrapper. Don't trust complex pattern matches yet — the doc spec is ahead of the implementation.

2. **`Option<T>` lowers to bare nullable.** `Option<Option<T>>` is not representable in the v0 emit — both `None` and `Some(None)` come out as `NULL`. The design doc specifies a tag-and-value lowering; v0 takes the shortcut. Avoid nested `Option`.

3. **Local type inference is shallow.** When a `let` value is a function call to *another module* or a complex chained call, you may get `l_x NUMBER;  -- TODO: inferred, please annotate`. Workaround: annotate the let with `let x: T = ...`.

5. **`@inline`, `@result_cache(relies_on = ...)`, `@error_code(N)` are still ignored.** The other annotations (`@deterministic`, `@result_cache`, `@udf`, `@autonomous`) now emit.

7. **No SQL validation.** The compiler doesn't check that table/column names inside `sql!{}` exist. Bind names are extracted from the SQL text by regex.

8. **No schema snapshot, no `pell.toml`, no `pell deploy`.** Those land in M4. For v0, the CLI is just `build`, `parse`, and `tokens`.

9. **Single-file modules only.** No cross-module imports beyond `import std::log;` (which doesn't even resolve, just prints as `log.info` in the body). Multi-file projects work if you compile each `.pell` separately, but cross-references aren't checked.

11. **Type-args (`::<T>`) only work on `.returning` and `.into`.** Generic `foo::<T>(...)` calls otherwise won't typecheck.

12. **No type checker.** Types are recorded but not really checked. Mismatches will surface at Oracle compile time, not pell compile time.

## The runtime

Every project that uses pell errors needs `pell_runtime` installed in the
schema. v0 ships a skeleton at `compiler/runtime/pell_runtime.sql`:

```sh
# in sqlcl or sqlplus, against your dev schema:
@compiler/runtime/pell_runtime.sql
```

After running it, each emitted module's `.sql` file contains a comment
block at the top that looks like:

```
-- Additions to pell_runtime for module hr.employees:
--   (collate these into a single CREATE OR REPLACE PACKAGE pell_runtime)
--   hr_employees_notfound EXCEPTION;
--   PRAGMA EXCEPTION_INIT(hr_employees_notfound, -20100);
```

v0.1 ships `pell runtime <dir> -o compiler/runtime/pell_runtime.sql` which
scans every `.pell` file in a directory, collects all error variants, and
emits a single merged `pell_runtime.sql` with the EXCEPTION declarations,
the `pell_err` context, and the `set_err`/`clear_err`/`get_err` helpers.
Re-run it whenever you add or remove an error variant; the codes are
assigned deterministically by file order, starting at `-20100`.

The earlier "paste it in by hand" workflow is gone — use `pell runtime`.

## Iterating on the compiler

```sh
# run tests after every change
cd compiler && PYTHONPATH=. .venv/bin/python -m pytest tests/ -v

# recompile examples (handy for snapshot diffing)
./pell build compiler/examples -d compiler/expected

# diff to see what changed
git diff compiler/expected/
```

The compiler is ~1500 lines of Python across four files. It's
deliberately small — most "bugs" are missing cases, not deep logic
problems. Add a failing test, add the case, watch it pass.

## Next steps

In rough order of payoff:

1. **Pick a real example to write end-to-end.** Take one of yours from
   the existing PL/SQL codebase, port it to pell, run `pell build`, and
   try the output against a sandbox schema. Whatever breaks is the v0.1
   roadmap.
2. **Wire up `@deterministic` / `@result_cache` / `@udf`** — the parser
   already collects them; the emitter just needs to render them onto the
   function signature.
3. **Better `Option<T>` lowering** — the tag-and-value form from §5 of
   the design doc.
4. **`match` arm pattern lowering** — make the emit faithfully reflect
   the AST.
5. **`pell check --db`** — the offline SQL parser tier from §11.3.
